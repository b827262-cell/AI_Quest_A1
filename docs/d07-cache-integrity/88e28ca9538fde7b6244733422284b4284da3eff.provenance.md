## Gate-D finding closed by this build

Codex re-ran Gate-D against `7b5e04f` and failed it on an executable source
blocker: after the learner pressed 「同意並前往 Google AI」, `page.tsx` called
`window.location.assign(url)`, so the consent action left the student page in the
same tab — against the Owner contract 「點擊同意後開 ONE 新分頁、保留原頁」.

`88e28ca` replaces that with `openConsentHandoffTab()`:

* one `window.open(url, "_blank")` per consent dialog, opener reference severed;
* called **without** a features argument on purpose — `noopener` in the third
  argument makes `window.open` return `null` even on success, which would read as
  a blocked popup and double-fire the fallback;
* blocked popup → a visible manual `target="_blank" rel="noopener noreferrer"`
  link, never a navigation (`openConsentHandoffTab` returns `"blocked"`);
* the one-shot budget guard lives in a `useRef` created when the dialog opens, so
  a repeated press returns `"duplicate"` and opens nothing;
* no auto-submit, no re-submit, no fetch/relay/scrape — the question only ever
  travels inside the Google URL, exactly as `buildGoogleAiModeUrl` builds it.

Regression coverage: 9 new cases in `site/tests/auto-fallback.test.mjs`
(one press → exactly one open; URL params `q`/`udm=50`/`aep=11`/`hl=zh-TW` and no
extra query keys; no features argument; duplicate press opens nothing; fresh
dialog gets its own budget; blocked popup and throwing `open()` never navigate;
missing `window` degrades to blocked; and a `page.tsx` source gate proving the
consent path routes through the helper and contains no
`location.assign|replace|href`, `requestSubmit`, `fetch` or `XMLHttpRequest`).
The source gate was negative-controlled against pre-fix `page.tsx`: it fails
there (`not ok 27`) and passes at `88e28ca`.

## Digests — this build instance only

```
PACKAGE_SHA    19af6e7a70a98c81d770eb72a4fb212c4fc70f8e6679af3c49ba79c5df279238
MANIFEST_SHA   00be97f7aeeffecffd2e97d613c346cf9328733abca4746cd3ad777ec6bb73a2
ROW_SET_DIGEST 50e126d4ab4aed85e2fa0c004d91fdc328d87307a8a4033041183a60e49dc80a
ARCHIVE_SHA256 b4c94ca450f6c0a06025ff1a6e5d26e18b500432178e8e1a01c51495594dd753
```

`PACKAGE_SHA` is the `verify-upload-package-size.mjs` digest over sorted
`path\0bytes\0sha256(file)\n` — order-insensitive by definition, since the gate
sorts the rows itself. `MANIFEST_SHA` is the sha256 of the tracked manifest file,
so it **does** depend on line order, and `ROW_SET_DIGEST` is the sha256 of the
path-sorted `[[path, bytes, sha256], …]` JSON (redundant with the other two; kept
because the metadata JSON carries it).

Because `MANIFEST_SHA` is order-sensitive, the tracked manifest is written by
`freeze-manifest.mjs` (this directory), which sorts rows as raw code units — the
same order the gate hashes in — and is therefore identical on any host. See
§Corrections for why the first revision of this record could not say that.

## Corrections

**2026-09-24, same-SHA re-review of `52baef6` (Codex). Finding: the first revision
of this record claimed the extracted manifest was *byte-identical* to the tracked
manifest. That was only ever true for the generator I used at freeze time, and
that generator was not reproducible.** Reviewers' own re-derivation produced the
same 99 rows in a different order, so the correct statement was 「row-set
identical」.

Root cause: the throwaway freeze script wrote the manifest lines from an array
sorted with `a.p.localeCompare(b.p)`. `localeCompare` is ICU/locale-driven, so the
**line order of the listing** — and therefore `MANIFEST_SHA`, which hashes the
file as bytes — depended on the host collation. Measured on the superseded tracked
manifest (`git show 52baef6:…frozen-manifest-19af6e7a.txt`, sha256 `ef984b53…`):
`LC_ALL=C sort -c` on its path column **fails at line 5** with
`disorder: .openai/drizzle/meta/0000_snapshot.json` — the locale collator had put
`_journal.json` ahead of the `00NN_snapshot.json` files it sorts between.

The same script computed `PACKAGE_SHA` and `ROW_SET_DIGEST` from a *separate*
array sorted in code-unit order, which is why those two digests were never
environment-dependent and why this correction moves exactly one value:
`MANIFEST_SHA`.

**74 of the 99 rows sit at a different line number after canonicalization; 25
keep theirs.** The small set of genuine re-orderings — the rest are cascade
shifts — is where locale collation disagrees with code units:

| Locale order (old) | Code-unit order (canonical) | Why they differ |
| --- | --- | --- |
| `.openai/drizzle/meta/_journal.json` ahead of `0000_snapshot.json` (old line 4) | behind all three `00NN_snapshot.json` (new line 7) | `_` = 0x5F outranks `0` = 0x30 in code units; the collator disagrees |
| `client/_headers` and the whole `client/_next/…` run ahead of `client/.assetsignore` (old line 22) | both dotfiles first, at new lines 9–10 | same `.` vs `_` rule |
| `server/__vite_rsc_assets_manifest.js` ahead of `server/.vite/manifest.json` and `server/BUILD_ID` (old lines 79–80) | those two first, at new lines 26–27 | same `.` vs `_` rule |
| `route-DjHd9EP4` ahead of `route-DYud2R__`, and `page-DlRzqwL4` ahead of `page-DN0jDwF6` | both pairs swapped | the collator case-folds the hash fragment; code units put `Y` before `j` and `N` before `l` |

Fix, docs-side only:

| Item | Before | After |
| --- | --- | --- |
| manifest generator | ad-hoc script under `/tmp`, `localeCompare` ordering | `freeze-manifest.mjs` (this directory, sha256 `580373960da3c15c3171989119cc84e8239fd79401167568582fc4017feb4cc8`), raw code-unit ordering, header comment forbids re-introducing locale-aware sorting |
| tracked manifest | `ef984b5372c827a9bef1c7e5fca5850acd399afdb8e28c8e500968d7ecca0913` | `00be97f7aeeffecffd2e97d613c346cf9328733abca4746cd3ad777ec6bb73a2` |
| wording | 「byte-identical」 without canonical evidence | 「byte-identical under canonical ordering」 backed by `cmp` + `LC_ALL=C sort -c`, plus the weaker row-set check spelled out separately |

**What did not change, and could not have:** the frozen package is a set of file
bytes, and `PACKAGE_SHA` is computed over rows the gate sorts itself, so
re-ordering a *record* of those rows cannot move it.

## Reproducibility: NOT reproducible

Six builds of byte-identical `site/` in this lane produced six different
`PACKAGE_SHA` values; two have retained evidence, and the two frozen archives
(`499fc11e…` for `af22d5a`, `b4c94ca4…` for `88e28ca`) each re-hash to their own
recorded digest. Root cause and consequences are written up in
`af22d5ad….provenance.md` (Vite/Rollup chunk-name rotation; `dist/` carries no git
SHA). This lane changes no build tooling and does not attempt a deterministic-Vite
fix — freezing one instance is the sanctioned workaround, per the Owner.

Comparing the two frozen archives' manifests (different source, so this is *not*
a pure nondeterminism sample, but it shows what the rotation costs):

| Observation | Value |
| --- | --- |
| `af22d5a` / `8fd53757` totals | 99 files / 2,712,148 B |
| `88e28ca` / `19af6e7a` totals | 99 files / 2,712,729 B |
| paths shared by both builds | 80 |
| of those, byte-identical | 68 |
| of those, same length but different content | 12 (embedded hash names swap at equal length) |
| paths unique to one build (name rotation) | 19 old-only + 19 new-only |
| where the +581 B actually went | `client/…/page-*.js` +291 B and `server/ssr/…/page-*.js` +290 B — the whole delta, and the only size change in the package |

So the consent fix costs 581 packaged bytes, and 19 further chunk names rotated
with no size change at all. Expect a fresh `npm run build` of `88e28ca` to produce
a **different** `PACKAGE_SHA` from a different name set; compare
`TOTAL_BYTES=2,712,729`, `MAX_FILE_BYTES=549044` and the manifest against this
archive instead.
